## 부록 A. Ansible로 Phase 1·2의 반복 작업을 줄일 수 있는가 — 타당성 검토 (v16 신설, 계획 단계·미구현)

**왜 검토했나**: Phase 1(3대)과 Phase 2 초입(2대)을 손으로 재현하는 데 시간이 오래 걸렸고, 그중 상당 부분이 (a) 서버마다 IP·호스트명만 다른 **같은 명령의 반복**, (b) 복붙 실수로 생긴 **재작업**(bond0 IP 오입력은 이 문서에서만 여러 번 기록됨)이었습니다. 이런 종류가 자동화의 가장 전형적인 대상입니다.

**결론(요약)**: 가능합니다. 다만 전 구간을 한꺼번에 하기보다, 반복이 많고 상태가 단순한 구간부터 나눠서 적용하는 게 현실적입니다.

| 구간 | 자동화 적합도 | 이유 / 주의 |
|---|---|---|
| §3 공통 설정 (호스트명, `/etc/hosts`, 관리망·bond0 nmcli, 패키지, chrony, sysctl, firewalld, SELinux boolean) | 높음 | 노드마다 값(IP)만 다름 → 변수 파일(`host_vars`)에 한 곳으로 모으면 복붙 실수가 구조적으로 사라집니다. 표준 모듈로 표현 가능(`hostname`, `dnf`, `template`, `community.general.nmcli`, `ansible.posix.firewalld`/`seboolean`/`sysctl`). v16 §3-5의 "호스트명 → IP" 매핑이 곧 `host_vars`의 원형입니다 |
| §4~§6 역할별 빌드 (httpd·AJP 프록시, Tomcat·`server.xml`·WAR, LVM·PostgreSQL) | 높음~중간 | 파일·패키지·서비스는 쉽습니다. LVM(`community.general.lvg`/`lvol`/`filesystem`/`mount`)은 디스크 지정만 잘하면 되고, v16의 '크기로 빈 디스크 선택'을 그대로 변수화하면 됩니다. `initdb`는 `command` + `creates: /pgdata/data/PG_VERSION`로 멱등화. PostgreSQL 사용자·DB는 `community.postgresql` 컬렉션이 편하지만 폐쇄망에서는 컬렉션 오프라인 반입이 필요합니다 |
| §4-6 로컬 저장소, §9-3 저장소 채우기 | 중간 | `dnf --downloadonly`가 "이미 설치돼 있으면 안 받는" 함정과, `--downloaddir`로 받은 파일이 나중에 지워지는 함정(§4-6 ⚠️ 2, 강한 추정)이 있어 `dnf download --resolve --alldeps --destdir`로 받는 방식으로 바꿨습니다. 스크립트화는 가능하나 `creates:` 등 멱등성 설계가 필요하고, 마지막에 rpm 개수 검증 단계를 넣는 것이 좋습니다 |
| §9-2, §9-4~§9-6 (bond0, hacluster 계정, 방화벽, `pcs host auth`/`cluster setup`) | 중간 | 앞쪽은 쉽습니다. `pcs` 명령은 멱등하지 않아 "이미 클러스터가 있으면 건너뛰기"(`pcs status` 성공 여부로 `when`) 처리가 필요합니다. RHEL 계열에 `ha_cluster` 시스템 롤이 있는 것으로 알고 있으나, 이 폐쇄망/Rocky 10에서 그대로 쓸 수 있는지는 **미확인**입니다 |
| §10(리소스·제약), §12~§14(수동 페일오버·PITR 드릴), §16(PAF·qdevice) | 낮음 — 손으로 유지 권장 | 상태·순서 의존이 크고, 애초에 "직접 장애를 내고 복구해 보는 것" 자체가 학습·포트폴리오 가치인 구간입니다 |

**Windows 호스트라는 제약 (중요)**: Ansible 컨트롤 노드는 Windows 네이티브로 동작하지 않습니다. 선택지는 세 가지입니다.

1. **Vagrant의 `ansible_local` provisioner** — 각 VM 안에 Ansible을 설치해 VM 안에서 실행합니다. 호스트에 아무것도 깔 필요가 없지만, 그 VM이 `ansible-core`를 받을 수 있어야 하고(Phase 1 초반처럼 인터넷이 되는 시점에만 적용 가능) 여러 노드에 걸친 순서를 표현하기가 불편합니다.
2. **WSL2에 Ansible 설치** 후 관리망(192.168.10.x)으로 SSH — 호스트 전용망에 WSL2에서 닿는지는 사전 확인이 필요합니다.
3. **컨트롤 전용 VM 1대(예: `ctl01`) 추가** — 이 프로젝트의 폐쇄망 구조(관리망 192.168.10.0/24)와 가장 잘 맞고 노드 간 순서 표현도 쉽습니다. 대신 VM이 하나 늘고 `ansible-core`를 로컬 저장소(§4-6)에 포함시켜야 합니다.

**3차 재현 세션이 알려준 `common` role의 설계 요구 (v16 추가)**:
- **'이미 적용된 상태'와 '아직 안 된 상태'가 노드마다 섞여 있습니다.** 호스트명·관리망 IP는 web01·was01에서는 Vagrant가 이미 설정했고 db01에서는 아니었습니다. role은 두 경우를 모두 통과해야 하며(`ok`/`changed`), 두 번째 실행에서 `changed=0`이 나오는지가 곧 이 검증입니다.
- **첫 접속 경로를 관리망 IP로 잡으면 안 됩니다.** db01처럼 관리망 IP가 아직 없는 노드가 실제로 있었으므로, 인벤토리는 Vagrant NAT 포트포워딩(`127.0.0.1:<포트>`)으로 시작하거나 `ansible_local`을 써야 부트스트랩이 막히지 않습니다.
- **`dnf update`는 자동화해도 빨라지지 않습니다.** 176 MB 다운로드가 노드당 5~11분(v16 추가 반영 5번)으로 네트워크가 병목이라 병렬 실행 외엔 줄일 방법이 없습니다. 줄이려면 업데이트가 반영된 box를 만들어 쓰는 방법이 있으나 이 프로젝트에서 검증하지는 않았습니다.

**권장 진행 순서 (제안)**:
1. 먼저 이 v16 문서 기준으로 수동 재현을 끝까지 성공시켜 **정답 상태**를 확정합니다. 잘못된 설계(이번의 IP 중복 같은)를 자동화하면 실수가 더 빨리 반복될 뿐입니다.
2. `common` role(§3)만 먼저 자동화합니다. 새 VM 한 대를 `vagrant up`한 뒤 playbook 1회로 §3까지 끝나는지 확인하고, 두 번 실행해도 `changed=0`(멱등)인지 확인합니다.
3. web/was/db 역할별 role(§4~§6)로 넓히고, 5대 재구축에 걸리는 시간을 수동과 비교합니다.
4. §9-2~§9-5(클러스터 준비까지)를 role로 만듭니다. 클러스터 생성 이후(§9-6~)는 당분간 수동으로 유지합니다.

**구조 스케치 (예시 — 모듈 파라미터는 실제 사용 시점의 컬렉션 버전 문서로 확인할 것)**:
```
ansible/
  inventory.ini          # [web] web01 web02 / [was] was01 was02 / [db] db01 db02
  host_vars/
    db01.yml             # mgmt_ip: 192.168.10.113 / bond_ips: ["10.10.10.13/24", "10.10.10.23/24"]
    web02.yml            # mgmt_ip: 192.168.10.121 / bond_ips: ["10.10.10.21/24"]
    ...                  # ← 이 파일들이 §0 주소 정리표의 '실행 가능한 버전'
  roles/{common,web,was,db}/   # tasks / templates / handlers
  site.yml
```
문서(이 가이드)와 role은 **둘 다 유지**하는 것을 권합니다. 손으로 한 번 해 본 절차가 있어야 자동화가 무엇을 하는지 설명할 수 있고, "수동으로 검증 → 자동화로 재현"은 그 자체로 포트폴리오에 남길 만한 이야기입니다.
