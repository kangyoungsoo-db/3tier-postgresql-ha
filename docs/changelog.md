# 3-Tier 폐쇄망 시스템 구성 실습 가이드 (Rocky Linux 10 기준) — v16 정리본 (Phase 1 + Phase 2 완료 + DB 복제·수동 페일오버·db01 재동기화·PITR 복구 드릴(§14)·pg_dump 논리 백업 자동화(§15)·Pacemaker DB 계층 자동 페일오버(§16) 완료)

> 원본 표본 구성도는 Rocky Linux 8.10 기준이지만, 이 가이드는 실제 구축 환경인 **Rocky Linux 10(v10.2)** 기준으로 전체 과정을 정리한 버전입니다. 네트워크 구조·서버 역할·IP 체계는 원본 구성도와 동일하게 유지하되, OS/미들웨어 버전 차이로 실제 달라지는 부분은 이유와 함께 명시합니다.

## ✅ Phase 1 완료

`사용자 → Apache(web01:80) → AJP → Tomcat(was01:8009) → JDBC → PostgreSQL(db01:5432)` 전체 트래픽 흐름이 실제로 끝까지 검증됐습니다(§7 End-to-End 5단계 전부 통과: db01 로컬 조회 → was01→db01 직접 psql → was01 Tomcat 직접 curl → web01 AJP 프록시 curl → 호스트 PC 외부 curl, 전부 `DB 연결 성공: appdb` / `StatusCode 200` 확인). 이 문서는 그 과정에서 실제로 겪은 문제들을 전부 반영한 최종본입니다.

## ✅ Phase 2 — 전체 완료 (VIP·리소스 전환·페일오버 테스트까지 검증)

web02/was02 추가, bond0 구성, 클러스터 패키지 설치, `pcs cluster setup`/`start`(§9)에 이어 web_vip(10.10.10.14)/was_vip(10.10.10.15) 등록, web02/was02에 httpd/tomcat 설치 및 AJP를 VIP 기준으로 재구성, httpd/tomcat을 pacemaker 리소스(`systemd:httpd`/`systemd:tomcat`)로 전환, 콜로케이션/순서 제약 설정까지 마쳤습니다(§10). 마지막으로 web01/was01을 각각 `pcs cluster stop`으로 강제 중단해 VIP+서비스가 web02/was02로 실제로 넘어가고, 그 상태에서도 `DB 연결 성공: appdb`가 정상적으로 나오는 것까지 페일오버 테스트로 직접 검증했습니다.

## ✅ Phase 2+ — db02 스트리밍 복제(Standby) 구성 완료

Phase 1·2가 끝난 뒤, DBA 지향 포트폴리오 보완을 위해 db02를 db01의 Standby로 붙였습니다(§11) — bond0 구성, db01과 동일 빌드로 PostgreSQL 설치, db01과 동일한 LVM 구조(pgdata/pgwal/pgbackup) 준비, 복제 계정·`pg_hba.conf` 설정, `pg_basebackup` 초기 동기화, db02 서비스 시작, `pg_stat_replication`에서 실제 `streaming` 상태 확인(db01에 쓴 데이터가 db02에서 즉시 조회되는 것까지 직접 검증), `listen_addresses` 수정, 재부팅 자동시작(`enable`)까지 전부 완료했습니다.

## ✅ 수동 페일오버 연습 완료 — 현재 db02가 Primary

db01을 실제로 내리고 db02를 `pg_promote()`로 승격시켜 쓰기 가능한 상태로 전환하는 것까지 검증했습니다(§12). 이 과정에서 Phase 1 때부터 조용히 실패하고 있던 **WAL 아카이빙 버그(`/pgwal` 소유권이 root:root였던 문제)**도 발견해 수정했습니다(§6-4에도 소급 반영). 이후 §13에서 db01을 `pg_basebackup`으로 db02의 새 Standby로 재동기화하고, 양쪽 모두 `wal_log_hints=on`까지 적용해 실제 로그로 검증을 마쳤습니다. §14에서는 §12-6에서 고친 WAL 아카이빙이 **실제로 복구에 쓸 수 있는지**를 DROP TABLE 재난 시나리오로 직접 증명했습니다(PITR). **지금 이 순간 기준으로 db02가 Primary, db01이 그 Standby로 정상 스트리밍 중**이며, PITR 복구 능력까지 검증된 상태입니다 — 새 대화에서 이어서 작업하실 경우 §15 맨 끝의 "현재 상태 스냅샷"을 꼭 먼저 확인하세요.

## ✅ pg_dump 논리 백업 자동화 완료 — db02에서 매일 02:00 자동 실행

§14 완료 후 남은 두 우선순위(논리 백업 자동화 / DB 계층 자동 페일오버) 중 논리 백업 자동화를 먼저 진행했습니다(§15). db02(Primary)에서 매일 02:00 `appdb`(pg_dump) + 전역 객체(role, `pg_dumpall --globals-only`)를 자동 백업하고 7일 지난 백업은 자동 삭제하도록 systemd timer로 구성했습니다. 진행 중 `/pgbackup`도 `/pgwal`과 똑같이 `root:root` 소유였던 것과, 데이터 디렉터리 안에 실행 스크립트를 두면 SELinux가 감사 로그에도 안 남기고 조용히 실행을 거부한다는 것을 새로 발견해 해결했습니다. 다음 단계(미정): Pacemaker를 이용한 DB 계층 자동 페일오버.

## v16 추가 반영 — 공통작업(§3) 3차 재현 기록(web01·was01·db01) 대조 결과

VM을 모두 지우고 v16 §2(`boot_timeout=900`)로 다시 만든 뒤 §3-1~§3-6을 손으로 끝까지 따라 한 기록 3개(web01.txt·was01.txt·db01.txt)를 v16과 한 줄씩 대조했습니다. 세 노드 모두 최종 검증(`✅ bond0 IP 일치`, 슬레이브 2개 `MII Status: up`, firewalld `active`, SELinux `Enforcing`)을 통과했고, 아래는 통과했지만 문서와 실제가 어긋났던 부분입니다.

1. **[확정] `vagrant up`이 끝까지 성공한 노드는 호스트명과 관리망(`enp0s8`) IP를 Vagrant가 이미 설정해 둡니다 — 그런데 db01은 그렇지 않았습니다.** web01·was01: 첫 `hostnamectl`이 `Static hostname: web01` / `was01`, §3-3 전의 `ip a`에 `enp0s8`이 `inet 192.168.10.111/24`(was01은 `.112`)를 이미 갖고 있었고 `nmcli con show`에 `enp0s8` 프로파일이 있었습니다(`ipv4.method: manual`). db01: `Static hostname: (unset)` / `Transient hostname: localhost`, `enp0s8`에 IPv4가 없고 프로파일도 없었습니다. 즉 v16 2번의 "타임아웃이면 후속 단계가 안 돈다"는 추정이 절반은 맞았습니다(끝까지 성공한 노드는 자동 적용). 다만 **db01만 왜 적용되지 않았는지는 미확정**입니다(이 노드만 부팅·SSH 응답이 유난히 늦었던 것과 관련 있을 가능성 — 추정). 부작용으로, §3-3이 '없을 때 실행할 명령'을 조건 없이 붙여넣기 쉬운 구조라서 web01·was01에서 `mgmt-net`이 중복 생성됐습니다(같은 NIC에 `enp0s8`=DEVICE `--` + `mgmt-net`; 같은 IP라 동작에는 지장 없음). **수정**: §3-1은 '확인 먼저', §3-3은 '상태 확인 → 호스트명으로 IP를 고르고 이미 있으면 건너뛰는 블록'으로 바꾸고 중복 정리법을 넣었습니다.
2. **[관찰] bond0 블록의 에러가 노드마다 달랐고, 결과는 모두 정상이었습니다.** web01·was01은 에러가 없었고(이전 세션들에선 매번 `A dependency of the connection failed`), db01은 `Connection '(null)' ((null)) successfully added.` / `The base network connection was interrupted` / `Unable to determine UID of the request`가 나왔지만 검증은 통과했습니다. 원인은 **미확정**입니다(후보: `dnf update` 직후 재부팅 전의 NetworkManager/D-Bus 상태, 활성 상태의 DHCP 대기 프로파일을 막 지운 직후). **수정**: 블록 마지막 재시도 줄이 실패해도 "아래 ✅가 통과하면 무시"라고 안내하도록 했고(§3-5, §9-2 공통), §3-5 설명을 실제 3가지 양상으로 고쳤습니다. 판정 기준(`✅` + 슬레이브 2개 `up`)은 이번에도 맞았습니다.
3. **[문서 공백] `dnf update`로 새 커널이 설치됐는데 재부팅 단계가 없었습니다.** 세 노드 모두 `Installed: kernel-core-6.12.0-211.60.1.el10_2`인데 실행 중 커널은 `6.12.0-211.16.1…`이었습니다. 재부팅하면 bond0·관리망 IP의 영구 저장 여부도 함께 검증되므로(특히 2번에서 에러가 났던 db01) **§3-7 '재부팅 후 확인'을 신설**했습니다(양방향 ping과 선택 스냅샷 포함).
4. **[안전 확인] v16 §3-5의 "`DEVICE` 열을 보고 지울 프로파일을 고른다" 절차가 3대 실제 실행에서 안전했습니다.** db01에서 활성(`connecting`) 상태였던 `Wired connection 1`·`4`와 미사용 `3`을 지웠을 때 SSH가 멈추지 않았고(NAT `Wired connection 2`는 건드리지 않음) 두 NIC이 `disconnected`로 정리됐습니다. web01·was01은 `--`(미사용) 프로파일 2개만 있었습니다. 프로파일 번호는 노드마다 달랐습니다(db01은 1·3·4, web01·was01은 1·4).
5. **[참고] `dnf update`(176 MB) 소요 시간이 컸습니다** — web01 4분 51초 / was01 6분 00초 / db01 11분 00초(db01은 `Curl error (28): Operation too slow` 미러 타임아웃 2건이 자동으로 다른 미러로 재시도됨). 문서 오류는 아니고 네트워크 속도 문제입니다. 세 창에서 동시에 실행하는 것이 가장 효율적이며, 다시 만들 일이 잦다면 §3-7의 스냅샷 지점을 활용하세요.
6. **[확인] §3-7 재부팅 결과 — 세 노드 모두 새 커널(6.12.0-211.60.1)로 부팅했고, 콘솔에 bond0이 올라온 것이 보였습니다. NAT 쪽도 세 노드 모두 `enp0s3 = 10.0.2.15/24`, `sshd active`, 22번 LISTEN이었습니다.** 다만 재부팅 직후 `vagrant ssh`가 메시지 없이 프롬프트로 돌아오는 시간이 있었고 원인은 미확정입니다(**§3-7에 안내 추가**). 아직 확인하지 못한 것: 재부팅 후 bond0의 실제 IP(특히 db01의 `.13`+`.23`)와 `nmcli con show --active` 출력.
7. **[챕터 4 web01 기록 대조] §4-1~§4-6(저장소 생성·SELinux·`200 OK`)은 가이드 순서대로 오류 없이 통과했습니다.** 어긋났거나 보강한 곳: (a) `grep proxy_ajp` 출력이 이미 활성(앞에 `#` 없음) → §4-2에 '이 경우 편집 불필요' 명시, (b) `AH00558` 경고 → 정상임을 명시, (c) `chronyc sources`가 재시작 직후 `^?`/`^x`뿐 → '몇 분 뒤 `^*` 확인'으로 판정 기준 명시(그 뒤 결과는 미확인), (d) lvm2만 받는 명령을 중복 실행(6개 전부 `SKIPPED`) → 불필요함을 명시, (e) `restorecon -Rv` 출력이 수백 줄 → 정상임을 명시, (f) **was01/db01용 저장소 등록 블록이 web01에서 실행돼 `local-web01.repo`가 생기고 외부 저장소(baseos/appstream/extras)까지 꺼져 `dnf repolist`에 `local-web01`만 남음** → §4-6에 경고와 되돌리는 명령(`rm`, `--set-enabled`), (g) **`httpd`는 이미 설치돼 있어 `--downloadonly`가 받지 않아 httpd 계열 12개가 로컬 저장소에서 빠짐**(출력 첫머리 `Package httpd-... is already installed.`) → `dnf download`로 채우는 명령 추가(미실행 명령이라 확인법 포함), (h) `java-21-openjdk`가 GUI 계열까지 끌고 와 245개·180 MB가 됨 → `headless` 대안을 '선택·미검증'으로 기재.
8. **[챕터 5 was01 기록 대조 — §5-1~§5-2 진행분] 설치는 가이드대로 통과했고(`java -version` OK, `tomcat9` 7개 패키지, `tomcat.service` 기동), 어긋난 곳이 둘 있었습니다.** (a) `systemctl show tomcat -p Environment`가 가이드의 '`CATALINA_BASE=…`로 나옵니다'와 달리 `Environment=NAME=`만 출력 — 이전 재현 기록에서도 똑같았으므로 **가이드 문구가 처음부터 틀렸던 것**이라 정정하고 `journalctl -u tomcat`의 `-Dcatalina.base=` 줄로 확인하도록 바꿨습니다, (b) 기동 1초 뒤에 `8080`을 확인해 `curl: (7) Failed to connect`가 났음 → '기다렸다가 `Server startup` 확인'을 추가(이후 결과는 미확인), (c) `java-21-openjdk`가 165개·150 MB인 것이 정상임을 §5-1에 명시. §5-3~§5-5도 통과했습니다(AJP 커넥터 추가, `[::ffff:10.10.10.12]:8009` LISTEN, chrony가 web01을 가리킴, 방화벽 규칙 등록) — 보강: (d) `ss` 출력의 `[::ffff:…]` 표기가 정상임, (e) `chronyc sources` 첫 출력이 `^?`·`-65.4s`여도 정상이며 재확인이 필요함, (f) **제가 앞서 '§5-3 restart 뒤에도 1~2분 걸릴 수 있다'고 쓴 것은 과했습니다** — 실제로는 바로 LISTEN이었고 첫 기동만 느렸으므로 §5-3 문구를 고쳤습니다.
9. 체크리스트에 50~88번을 추가했고, 부록 A에 '3차 세션이 알려준 `common` role 설계 요구'를 덧붙였습니다.
10. **[챕터 5 was01 기록 대조 — §5-6~§5-8 진행분] WAR 배포, 8009 접근 제어 검증, 커널 파라미터 적용, 최종 확인 명령까지 오류 없이 실행됐습니다(chrony는 `^*`까지 확인했고, 시계 안정성 문제는 아래 (d)·(g)).** `unzip -l`로 `HealthController.class`가 WAR 안에 있음을 확인했고(파일 시각 13:00 — 세 번째 빌드본), `app.war`가 배포돼 `/app/db-check`가 응답했습니다(500, 아래 (e)). 로그에서 가이드와 어긋났거나 보강한 곳: (a) **앱이 두 번 기동됨** — Tomcat 로그에 `Started AppApplication in 159.89 seconds` → `Root context already created (using as parent).` → `Started ServletInitializer in 7.327 seconds`가 이어지고 `Filter errorPageFilter was not registered (possibly already registered?)`도 찍혔습니다. §5-6-3 참고 박스가 '충돌할 가능성'이라고만 적었던 부분이 실제로 나타난 것이라, 박스를 로그 근거와 해결(`ServletInitializer.java` 삭제)로 고쳤습니다. 삭제 뒤 결과는 **미확인**입니다. (b) **WAR 포함 재시작이 약 4분 15초** — `deployWAR … has finished in [248,736] ms`, `Server startup in [255146] milliseconds`. 대부분은 Spring 첫 기동 159.89초(그중 `Root WebApplicationContext: initialization completed in 69701 ms`)입니다. §5-6-7에 대기 안내를 넣었습니다. 왜 이렇게 느린지는 **미확정**입니다. (c) **§5-5의 8009 확인 결과** — web01 `OPEN`, db01 `BLOCKED`(`bash: connect: No route to host`와 함께). '미실행' 표기를 결과로 바꾸고, `No route to host`가 방화벽 거부로 보인다는 설명을 넣었습니다. 1. **[근본 원인 확정] web02/was02 → web01/was01 방향만 안 되던 문제는 ARP·방화벽·커널 파라미터가 아니라 "IP 중복"이었습니다.** — v15 §3-5는 web01 bond0에 `10.10.10.11`과 "서비스 IP" `10.10.10.21`을 **둘 다** 주게 했고, 같은 문서 §9-2는 web02 bond0에 `10.10.10.21`을 줬습니다. 그대로 따라 하면 web01과 web02가 `10.10.10.21`을 동시에 갖게 됩니다(was01의 `.22` ↔ was02의 `.22`도 동일). 기록상의 증거: web01의 `ip a show bond0`에 `inet 10.10.10.21/24 ... scope global secondary`가 있고(web01.txt), web02는 `ipv4.addresses "10.10.10.21/24"`로 같은 주소를 설정했으며(web02.txt), web02의 `ip neigh show`에는 `10.10.10.11 dev bond0 FAILED`가 남았습니다. 반대 방향이 "잘 되는 것처럼" 보였던 이유는, web01이 `ping 10.10.10.21`을 했을 때 그 주소가 **web01 자기 자신의 주소**라서 패킷이 케이블에 나가지도 않고 로컬에서 응답했기 때문입니다(응답 `time=0.113 ms` 같은 비정상적으로 빠른 값이 web01 기록에 실제로 찍혀 있습니다). 새 노드→구 노드 방향은 ARP 요청의 출발지 IP가 구 노드 자신의 주소와 같아져서 응답이 오지 않았습니다(리눅스가 출발지 주소가 자기 로컬 주소인 패킷을 정상 트래픽으로 취급하지 않는 동작 때문으로 **추정**합니다 — 기록상의 `FAILED`와 일치하지만 커널 내부 동작을 이 환경에서 직접 확인한 것은 아닙니다). v6 업데이트 7번과 §9-1 노트의 "실제로는 21/22를 노드 IP로 먼저 써서 클러스터를 완성했다"는 기록도 이 해석과 맞습니다 — 원본 빌드에서는 web01/was01에 세컨더리 `.21/.22`가 애초에 없었던 것으로 보이며, §0·§3-5의 문서 설명만 두 IP 체계로 앞서 있었던 것으로 **추정**합니다. **수정**: web01/was01 bond0는 기본 IP 하나만(`.11`/`.12`), `.21/.22`는 web02/was02의 노드 IP로만 사용(§0 주소 정리표·§3-5·§9-2). db01의 `.23`은 §11·§16에서 실제로 쓰이는 예약 IP라 그대로 둡니다. §9-2에 사전 점검(`ip route get`)과, 이미 세컨더리를 붙여버린 환경의 복구 절차를 추가했습니다.
2. **`vagrant up`이 `Timed out while waiting for the machine to boot`로 실패 — web02·was02에서 모두 재현(그 전 노드에서도 같은 증상이 보고됨)** — v15 Vagrantfile에는 `boot_timeout`이 한 줄도 없어서 Vagrant 기본값(300초)이 적용됐습니다. 그런데 실제로는 VM이 부팅되고 있었습니다(타임아웃 뒤 `vagrant ssh`가 바로 성공, `vagrant status`도 5대 모두 `running` — web02.txt/was02.txt). VM이 아니라 **Vagrant가 먼저 포기한 것**입니다. **수정**: §2 Vagrantfile에 `config.vm.boot_timeout = 900`을 추가했고, 이 프로젝트는 호스트↔게스트 공유 폴더를 쓰지 않으므로(파일은 `python -m http.server`/`curl`로 전달) `synced_folder ... disabled: true`도 함께 넣어 마운트 시도 자체를 없앴습니다. **부수 효과(추정)**: 타임아웃으로 `vagrant up`이 중간에 끝나면 그 뒤 단계(호스트명 설정, `private_network` IP 설정)가 실행되지 않습니다 — web02/was02에서 `hostname`이 `localhost.localdomain`이었던 것이 그 증거이고, §3-1·§3-3의 수동 확인 단계가 필요했던 이유일 가능성이 큽니다(→ 타임아웃을 늘려 다시 만든 3차 세션에서 부분적으로 확인됐습니다: 바로 위 "v16 추가 반영" 1번).

5. **`lsblk` 디스크 문자가 또 달라짐 — 이번 db01은 `sda(20G)` / `sdb(5G)` / `sdc(10G, OS·파티션 있음)` / `sdd(5G)`** — v15 §6-2와 §11-5는 `sdb=20G, sdc=5G, sdd=5G`를 가정한 `pvcreate /dev/sdb /dev/sdc /dev/sdd`를 적어놨습니다. 이번 환경에서 그대로 실행했다면 **OS 디스크(sdc)를 PV로 만들려는 명령**이 됐을 것입니다(사용자는 `lsblk`를 보고 `pvcreate /dev/sda /dev/sdb /dev/sdd`로 직접 바꿔 피했습니다). 디스크 문자는 VM·부팅마다 바뀔 수 있으므로(이전 db01 기록에서도 다른 매핑이었습니다) §6-1·§11-5를 '**파티션 없는 빈 디스크만 크기와 함께 출력 → 변수에 대입 → 변수로 LVM 생성**' 방식으로 바꿨습니다(OS 디스크는 파티션이 있어 후보에서 자동으로 빠집니다).
6. **was01 Tomcat AJP가 처음엔 `[::1]:8009`에만 뜨고 `secretRequired="true"` 예외로 시작 실패 — `server.xml`을 vim으로 6번 고치고서야 성공** — 기본 `server.xml`의 주석 처리된 AJP 블록은 `address="::1"`이고 `secretRequired` 속성이 없어서, 주석만 풀면 journalctl에 `IllegalArgumentException: The AJP Connector is configured with secretRequired="true" but the secret attribute is either null or ""`가 찍히면서 커넥터가 시작하지 못하거나 `::1`에만 바인딩됩니다(was01.txt의 `ajp-nio-0:0:0:0:0:0:0:1-8009`, `ss -tnlp`의 `[::1]:8009`). v15 §5-3은 '주석을 풀거나 새로 추가'라고만 적어서 위치와 속성을 손으로 맞춰야 했습니다. §5-3에 **스크립트 방식**(주석 밖에 살아있는 AJP 블록이 없을 때만 정확한 Connector를 `</Service>` 앞에 추가, 원본은 `server.xml.orig`로 백업)을 1순위로 넣고 수동 방법은 주의점과 함께 남겼습니다.

## v14 업데이트 — pg_dump 논리 백업 자동화(§15) 신규 작성, 진행 중 새로 발견한 것

§14 PITR 검증 완료 후 남은 두 우선순위 중 논리 백업 자동화를 먼저 진행하며 §15를 신규 작성했습니다. db02(Primary)에서 appdb + 전역 객체(role)를 매일 02:00 자동 백업하고 7일 지난 백업은 자동 삭제하도록 구성했습니다.

1. **`/pgbackup`도 `/pgwal`과 똑같이 `root:root` 소유였음 — postgres 계정이 애초에 그 안에 쓸 수 없는 상태였음** — §12-6에서 `/pgwal`만 고쳤을 뿐 `/pgbackup`은 그대로 남아 있었습니다. `touch` 테스트로 즉시 재현(`Permission denied`) 후 `chown postgres:postgres /pgbackup`로 해결했습니다(§15-2).
2. **데이터 디렉터리(`postgresql_db_t` SELinux 컨텍스트) 안에 실행 스크립트를 두면 systemd가 조용히 실행을 거부함 — 그것도 감사 로그에 안 남는 `dontaudit` 규칙이라 진단이 특히 어려웠음** — 권한(`chmod 700`, 소유자 `postgres`)은 전부 맞는데도 `systemctl start`가 `203/EXEC ... Permission denied`로 실패했습니다. 같은 파일을 `sudo -u postgres`로 직접 실행하면 성공하는데 systemd로 띄우면 실패해 처음엔 원인을 좁히기 어려웠고, `ausearch -m avc`에도 아무 기록이 없어 더 헷갈렸습니다. `setenforce 0`(permissive)로 임시 전환하자 즉시 성공해 SELinux가 원인임을 확정했고, 되돌린 뒤(`setenforce 1`) 근본 해결로는 스크립트를 데이터 디렉터리 밖(`/usr/local/bin`, 기본 `bin_t` 컨텍스트)으로 옮기고 `BACKUP_DIR`(백업 산출물이 실제로 쌓이는 곳)만 `/pgbackup`으로 유지했습니다(§15-4). **교훈: 데이터 전용 디렉터리(`*_db_t`)엔 실행 파일을 두지 말 것 — 스크립트는 표준 실행 경로에, 산출물만 데이터 디렉터리에.**
3. **db01의 기존 §6-9 백업 스크립트(Phase 1 때 작성)도 같은 뿌리 문제를 안고 있을 가능성이 높음 — ✅ 이후 진단·폐기까지 완료(§15-8)** — db01의 `/pgbackup`을 확인해보니 여전히 `root:root`였고, cron(`0 2 * * *`)은 등록돼 있지만 실제 백업 파일(`backup_*.dump`)은 하나도 없었습니다. Phase 1 이후 지금까지 매일 밤 조용히 실패해왔을 것으로 추정됐고(§15-6), 실제로 재확인해보니 그 추정이 전부 맞았습니다. db01은 §13 이후 Primary가 아니라 Standby이고 논리 백업의 정본은 이미 §15가 맡고 있으므로, 이 cron은 고치지 않고 **폐기**했습니다 — crontab 제거, 스크립트는 `pg_backup.sh.disabled`로 흔적만 보존, `/pgbackup` 소유권도 postgres로 정리(§15-8).

## v13 업데이트 — PITR(시점 복구) 드릴 완료(§14), 진행 중 새로 발견한 것

§12-6에서 고친 WAL 아카이빙이 "카운터만 올라가는지" 아니면 "실제로 복구에 쓸 수 있는지"를 한 번도 증명한 적이 없어서, DROP TABLE 재난 시나리오를 직접 만들어 검증했습니다. 별도 포트(5433)의 독립 인스턴스로 복구해 원본 서비스는 전혀 건드리지 않았고, 최종적으로 재난 이전 데이터만 남고 이후 데이터는 없는 상태로 정확히 복구되는 것까지 확인했습니다. 과정에서 실제 장애 두 건을 만나 원인을 좁혀 해결했습니다.

1. **`mkdir`로 먼저 만든 디렉터리에 `pg_basebackup`을 뜨면 권한이 `0700`으로 자동 정정되지 않음** — `initdb`는 데이터 디렉터리 권한을 알아서 `0700`으로 만들어주지만, 이미 존재하는(기본 umask로 생성된 `0755`) 디렉터리에 `pg_basebackup`을 뜨는 경우엔 그렇지 않았습니다. `cp -a`로 복사한 사본에도 그 `0755`가 그대로 전달돼, PostgreSQL이 "data directory has invalid permissions"로 기동을 거부했습니다. `chmod 700`으로 해결(§14에 재발 방지 체크리스트로 반영).
2. **복구 목표 지점이 하필 아직 아카이브되지 않은 WAL 세그먼트 안에 있었음** — `pg_create_restore_point`로 지점을 찍어도, 그 지점이 포함된 WAL 세그먼트(16MB 단위)가 다 차서 다음 파일로 넘어가기 전까진 아카이버에게 안 넘어갑니다. 이번 드릴처럼 트랜잭션 몇 개로는 16MB를 채우기엔 턱없이 부족해, 복구가 그 세그먼트 직전에서 "recovery ended before configured recovery target was reached"로 멈췄습니다. `pg_switch_wal()`로 강제로 세그먼트를 넘겨 아카이브시킨 뒤 재시도해 해결(§14에 실전 교훈으로 반영 — 운영 환경에서도 재해 직후 그대로 나올 수 있는 함정입니다).

## v12 업데이트 — §13 실제 실행 완료, 진행 중 새로 발견한 것

§13을 실제로 처음부터 끝까지(13-1~13-4) 실행하고 실제 로그를 반영했습니다. 사전 예상(pg_rewind 조건 미충족 → pg_basebackup 경로)은 정확히 들어맞았지만, 그 과정에서 예상 못 했던 문제 두 가지를 더 만나 해결했습니다.

1. **13-3 검증 중 — INSERT가 성공 메시지를 냈는데도 db02 자신에게서조차 사라짐** — db02에서 `INSERT INTO promote_test VALUES (now());`가 `INSERT 0 1`까지 정상 출력됐지만, 곧이어 db01은 물론 **db02 자기 자신도 다시 조회하면 그 값이 없고 `pg_current_wal_lsn()`도 그 전후로 전혀 안 움직인** 상태였습니다. 처음엔 db01의 복제 지연을 의심했지만, LSN을 직접 비교해보니 db01은 이미 db02와 완전히 같은 위치에 있었고, 문제는 db01이 아니라 db02에서 그 트랜잭션이 애초에 커밋까지 못 갔다(롤백됐다)는 쪽으로 좁혀졌습니다. INSERT와 확인용 SELECT를 같은 psql 세션에 붙여서 실행하니 문제없이 재현됐습니다(13-3에 재발 방지 습관 반영).
2. **13-4 중 — `pg_controldata`의 "OO setting" 항목은 라이브 설정이 아니라 마지막 checkpoint/restartpoint 시점의 스냅샷이라는 것을 실제로 확인** — db01(Standby)에서 `wal_log_hints=on`을 설정하고 재시작까지 했는데도 `pg_controldata`는 계속 `off`로 나왔습니다. `SHOW wal_log_hints;`로 라이브 값은 이미 `on`임을 확인했고, `CHECKPOINT;`(recovery 중엔 자동으로 restartpoint 처리)를 강제로 걸어주자 즉시 `pg_controldata`에도 `on`으로 반영됐습니다. (v16 r24 정정: 처음부터 다시 재현한 PC에서는 이 방법이 통하지 않았고, Primary(db02)를 켜고 재시작한 뒤에 반영됐습니다 — §13-4.) Primary(db02)는 재시작 자체에 기동 체크포인트가 포함돼 즉시 반영됐지만, Standby는 별도로 강제해줘야 한다는 차이를 실전에서 확인했습니다(13-4에 반영). **이건 pg_rewind 사전 점검(13-1)에도 그대로 적용됩니다** — Standby에 `wal_log_hints`를 켠 뒤 pg_rewind를 준비 중이라면, 최소 한 번은 `CHECKPOINT;`로 강제 반영해둬야 실제로 조건을 충족한 상태가 됩니다.

## v11 업데이트 — db01 재동기화 절차(§13) 신규 작성

§12 끝의 "현재 상태 스냅샷"(db02가 Primary, db01 정지)을 이어받아 db01을 db02의 새 Standby로 되돌리는 §13을 작성했습니다. **§12까지와 달리 §13은 아직 실행 로그로 검증되지 않은 절차입니다** — 실행 후 실제 결과를 알려주시면 다음 버전에 반영합니다.

1. **`pg_rewind`를 쓰려면 target(db01)이 갈라지기 전부터 `wal_log_hints=on` 또는 데이터 체크섬이 켜져 있어야 하는데, 이 프로젝트는 처음부터 둘 다 켠 적이 없음** — §6-4의 `initdb` 명령에 `--data-checksums`가 없고, §6-7 `postgresql.conf`에도 `wal_log_hints`를 설정한 적이 없습니다. 이 설정은 지금 켜도 과거 WAL에는 소급 적용되지 않으므로, 이 프로젝트 환경에서는 `pg_rewind`가 곧바로 조건 미충족 에러로 거부될 가능성이 높습니다(13-1에서 직접 확인 절차 제공).
2. **그래서 이번엔 `pg_rewind` 대신 §11과 동일한 `pg_basebackup` 방식으로 db01을 재구성하는 경로를 기본으로 안내**합니다(13-2) — 방향만 반대(db02가 source, db01이 target)이고 나머지 패턴은 §11과 동일합니다.
3. **db02의 `pg_hba.conf`에는 db01發 복제 접속을 허용하는 규칙이 없다는 점을 새로 짚었습니다** — db02는 원래 db01을 복제해 만들어졌으므로, db02의 `pg_hba.conf`엔 "db02 자신이 복제해도 된다"는 규칙만 있고 "db01이 복제해도 된다"는 규칙이 없습니다. 방향이 뒤집혔으니 반대쪽 규칙을 추가해야 합니다(13-2-2).
4. **다음번 승격 연습부터는 진짜 `pg_rewind`를 쓸 수 있도록, db01·db02 모두 `wal_log_hints=on`으로 켜두는 절차를 선택 항목으로 추가**했습니다(13-4).

## v10 업데이트 — 수동 페일오버 연습(§12) 중 발견한 것

§11에서 복제까지 마친 뒤, 실제로 db01을 내리고 db02를 승격시키는 페일오버 연습을 진행하며 §12를 신규 작성했습니다.

1. **자동 페일오버는 저절로 안 일어남 — 순수 스트리밍 복제의 한계** — db01이 죽어도 db02는 계속 재접속만 시도할 뿐 스스로 승격하지 않습니다. 사람이 직접 `pg_promote()`를 호출해야 합니다(§12-4, §12-5). 이 지점이 나중에 Pacemaker+PAF로 자동화할 대상입니다.
2. **`/pgwal` 디렉터리가 `root:root` 소유라, WAL 아카이빙이 Phase 1 때부터 지금까지 계속 조용히 실패하고 있었음** — §6-7에서 `archive_mode=on`을 켰지만 실제로 검증한 적이 없어서 아무도 몰랐던 문제입니다. db02 승격 시 새 타임라인 `.history` 파일을 아카이브하려다 `Permission denied`로 걸리면서 발견됐습니다. **§6-4의 `chown` 명령에 `/pgwal`을 추가해 원인 자체를 소급 수정**했습니다 — 처음부터 이 가이드를 다시 따라 하면 이제 이 버그를 겪지 않습니다(§12-6).
3. **되돌릴 수 없는 작업 전엔 VirtualBox 스냅샷** — `pg_promote()`는 새 타임라인을 시작하는 명령이라 간단히 원복이 안 됩니다. 실행 전 스냅샷을 떠두면(§12-1) 문제 생겨도 바로 복원 가능합니다.

## v9 업데이트 — db02 복제 마무리(§11-9~§11-13) 중 실제로 겪은 문제들

§11의 나머지(서비스 시작 → 실제 복제 확인 → `listen_addresses` 문제 발견/수정 → 자동시작 활성화)를 마무리하며 아래를 반영했습니다.

1. **`pg_basebackup`이 db01의 `postgresql.conf`를 통째로 복사해오면서 `listen_addresses`에 db01 자신의 IP(`10.10.10.13`)가 그대로 남아있음** — db02 로그에 `could not bind IPv4 address "10.10.10.13"` 경고가 남습니다. 복제 자체(db02가 db01에게 먼저 접속을 거는 방향)엔 지장 없지만, db02가 직접 트래픽을 받거나 승격되기 전에 반드시 `10.10.10.24`로 고쳐야 합니다(§11-11).
2. **가장 확실한 복제 검증은 "상태 조회"가 아니라 "실제로 써보는 것"** — `pg_stat_replication`의 `state: streaming`만으로는 안심이 덜 돼서, db01에 테스트 테이블을 만들고 db02에서 즉시 조회되는지, `DROP` 같은 DDL도 복제되는지까지 실제로 확인했습니다(§11-10).
3. **`systemctl enable`은 모든 검증이 끝난 뒤 마지막에** — 문제가 있는 상태로 미리 `enable`해두면 재부팅 시 그 문제가 그대로 반복될 수 있어, 검증 순서를 의도적으로 맨 뒤로 뒀습니다(§11-12).

## v8 업데이트 — db02 스트리밍 복제 구성 중 실제로 겪은 문제들 / 확인한 사실들

DB 계층 이중화(db02 추가 + PostgreSQL 복제)를 시작하면서 확인한 사실과 겪은 문제를 반영해 §11을 신규 작성했습니다.

1. **로컬 저장소(local-web01)엔 PostgreSQL 패키지가 아예 없음 — HA 패키지만 있음** — §9-3에서 `highavailability` 저장소만 채워 넣었을 뿐, PostgreSQL은 애초에 로컬 저장소 대상이 아니었습니다(§11-3).
2. **db01이 실제로 쓰는 건 PGDG의 `postgresql16-server`가 아니라 Rocky AppStream의 무버전 `postgresql-server`(빌드 `16.14-1.el10_2`)** — 기존 "이전 v3/v4 개정" 항목엔 "16 채택"이라고만 기록돼 있었는데, db02를 준비하며 정확한 패키지명·빌드까지 재확인했습니다. **복제는 Primary/Standby가 완전히 동일한 빌드여야 안전**하므로, db02도 반드시 같은 경로(AppStream)에서 설치해야 합니다 — PGDG로 깔면 겉보기엔 같은 "16"이라도 바이너리·경로가 달라 위험합니다(§11-3).
3. **db01의 PGDATA는 기본 경로(`/var/lib/pgsql/data`)가 아니라 `/pgdata/data`로 override돼 있음** — Phase 1 때 만든 systemd override(`/etc/systemd/system/postgresql.service.d/override.conf`)를 db02에도 똑같이 복사해야 합니다. 빠뜨리면 db02의 PostgreSQL이 기본 경로를 보게 되어 애써 받은 백업이 무용지물이 됩니다(§11-5).
4. **Standby는 `initdb`로 만들면 안 됨** — `initdb`는 db01과 무관한 완전히 새 클러스터를 만들어서, 나중에 복제 연결 자체가 거부됩니다. `pg_basebackup`으로 db01의 데이터를 통째로 복사해야 하며, 그 전까지 `/pgdata/data`는 권한만 맞추고 비워둬야 합니다(§11-5, §11-7).
5. **`pg_basebackup` 실행 시 `PGPASSWORD=값 sudo ...` 순서로 쓰면 안 됨** — `sudo`는 기본적으로 대부분의 환경변수를 걸러내므로, `PGPASSWORD`를 `sudo`보다 앞에 두면 무시됩니다. `sudo -u postgres env PGPASSWORD=값 pg_basebackup ...`처럼 `env`로 감싸 `sudo` 뒤에 둬야 실제로 전달됩니다(§11-7).
6. **복제 계정과 앱 계정은 분리** — 기존 `app_user`(§6)를 재사용하지 않고, `REPLICATION` 권한만 가진 별도 `replicator` 계정을 새로 만들었습니다(§11-6).
7. **서비스망 IP는 db01처럼 기본+서비스 2개를 다 주지 않고 db02엔 1개만** — db01은 실제로 `10.10.10.13`(기본) + `10.10.10.23`(서비스/향후 VIP 후보)을 둘 다 갖고 있는 상태입니다. db02는 `10.10.10.23`을 그대로 가져다 쓰면 db01과 충돌하므로, `10.10.10.24` 하나만 부여했습니다(§11-2). 향후 DB 계층까지 Pacemaker로 자동 페일오버를 구성한다면, web/was 때처럼 이 `10.10.10.23`이 VIP 후보가 됩니다.

## v7 업데이트 — Phase 2 마무리(§10) 중 실제로 겪은 문제들

§10(VIP 등록 → httpd/tomcat 재구성 → pacemaker 리소스 전환 → 페일오버 테스트)을 진행하면서 아래 문제들이 실제로 발생했고 전부 원인을 찾아 고쳤습니다. §10을 신규 작성해 반영했습니다.

1. **`sudo cat > 파일 <<EOF`가 Permission denied** — `>` 리다이렉션은 sudo가 적용되기 전에 지금 로그인한 셸이 먼저 처리해서, 여전히 일반 계정 권한으로 파일을 열려고 시도함. `sudo tee 파일 <<EOF`로 해결(§10-2-1).
2. **web02에 `mod_ssl` 설치 후 `apachectl configtest`가 `SSLCertificateFile ... does not exist` 로 실패** — 자체서명 인증서가 자동 생성되지 않음. 이 프로젝트는 애초에 HTTPS를 쓰지 않으므로 `ssl.conf` 자체를 비활성화하는 것으로 해결(§10-2-1).
3. **web01의 AJP 프록시가 was01 고정 IP(10.10.10.12)를 직접 바라보고 있어 HA가 무의미했음** — was가 페일오버돼도 web은 계속 죽은 was01만 찾게 됨. was_vip(10.10.10.15)로 재조정(§10-2-2).
4. **AJP 프록시가 503으로 실패, 에러 로그에 `(111)Connection refused ... 10.10.10.15:8009`** — was01 Tomcat의 AJP Connector가 `address="10.10.10.12"`로 고정 바인딩돼 있어 VIP 주소로는 아무도 안 듣고 있었음. 방화벽이 이미 소스 IP를 제한하고 있으므로 `address="0.0.0.0"`으로 풀어도 안전함(§10-2-2).
5. **was02에 Tomcat 설치 후 8080은 뜨는데 8009(AJP)만 안 뜸** — AJP Connector에 `secretRequired="false"`가 빠지면 Ghostcat(CVE-2020-1938) 대응으로 커넥터 자체가 조용히 초기화를 거부함. was01과 완전히 동일하게 `secretRequired="false"`까지 넣어야 함(§10-2-5).
6. **WAR 파일 전달용 임시 서버가 `OSError: [Errno 98] Address already in use`** — Tomcat 자신이 이미 8080(HTTP 커넥터)을 쓰고 있어 포트가 겹침. 8090 등 다른 포트 사용(§10-2-7).
7. **was02에 `wget` 명령 자체가 없음** — Rocky 최소 설치 이미지엔 기본 미포함. `curl -O`로 대체(§10-2-7).
8. **`pcs cluster stop <노드>`를 그 노드 자신에서 실행한 뒤, 같은 노드에서 `pcs status`/`curl`이 실패** — 정상 동작입니다. 방금 corosync/pacemaker를 끈 노드는 자기 자신에게 상태를 물어볼 대상이 없어짐. 페일오버 확인은 항상 **살아있는 반대쪽 노드**에서(§10-4).
9. **페일오버 테스트에서 was_vip/was_tomcat이 was02로 안 넘어가고 계속 `Stopped`로 남음** — `Failed Resource Actions`에 훨씬 이전(과거 시점) 실패 기록(`Not installed`)이 남아있으면, Pacemaker가 그 노드를 리소스 후보에서 영구 제외함. `pcs resource cleanup <리소스명>`으로 오래된 실패 기록을 지워야 재평가함(§10-4).

## v6 업데이트 — Phase 2 준비(§9) 중 실제로 겪은 문제들

§9(web02/was02 추가 + 클러스터 구성)를 진행하면서 아래 문제들이 실제로 발생했고 전부 원인을 찾아 고쳤습니다. §9를 전면 재구성해 반영했습니다.

1. **`dnf install --downloadonly`가 이미 설치된 패키지를 그냥 건너뜀** — web01엔 pacemaker/corosync/pcs/resource-agents가 이미 설치돼 있어서, 로컬 저장소를 채우려던 `--downloadonly` 명령이 매번 "Nothing to do"로 끝나며 실제로는 rpm을 하나도 못 받아왔습니다(§9-3).
2. **pacemaker 계열 패키지가 BaseOS/AppStream이 아니라 별도 `highavailability` 저장소 소속, 기본 비활성화 상태** — 이걸 활성화 안 하면 뭘 해도 `No match for argument: pacemaker`가 뜹니다(§9-3).
3. **`mv`로 옮긴 rpm 파일이 Apache에서 403 Forbidden** — `mv`는 원본 위치의 SELinux 컨텍스트를 그대로 가져와서 `httpd_sys_content_t`가 아니게 됩니다. `restorecon -Rv`로 해결(§9-3).
4. **`pcs host auth`에서 `Could not resolve host: web02`** — `/etc/hosts` 미등록 상태에서 이름으로 인증을 시도한 것. `addr=`로 IP를 직접 지정해 우회(§9-6), 재발 방지를 위해 `/etc/hosts` 등록 단계도 별도로 추가(§9-7).
5. **`pcs host auth`에서 `port 2224 ... Could not connect to server`** — firewalld가 기본적으로 pcsd/corosync 포트를 막고 있었음. `high-availability` 서비스 개방으로 해결(§9-5).
6. **클러스터 기동 직후 노드가 전부 `UNCLEAN (offline)`, was-cluster는 로컬 노드 자신조차 offline** — corosync나 방화벽이 아니라 **web02/was02에 서비스망 bond0 자체가 아예 안 만들어져 있던 것**이 근본 원인이었습니다(`ip -4 addr show bond0` → `Device "bond0" does not exist`). 기존 9-1 노트가 "§4/§5만 반복하면 된다"고 안내했는데 정작 bond0(원래 §3-5)이 빠져 있었던 것 — §9-2로 명확히 분리해 추가했습니다.
7. **서비스 IP 주소 체계가 처음 계획과 다르게 확정됨** — 원래 계획은 web02=10.10.10.14, was02=10.10.10.15를 노드 IP로 쓰고 10.10.10.21/22는 나중에 VIP로 비워두는 것이었지만, 실제로는 21/22를 노드 IP로 먼저 써서 클러스터까지 완성했습니다. 이 문서는 실제 값 기준으로 통일했고, VIP는 대신 10.10.10.14/15를 쓰는 것으로 계획을 조정했습니다(§9-9). ⚠️ 이미 진행하셨다면 다시 바꾸실 필요 없습니다.

## v5 업데이트 — Phase 1 마무리 중 실제로 겪은 문제들

§7 End-to-End 테스트를 진행하면서 아래 문제들이 실제로 발생했고, 전부 원인을 찾아 고쳤습니다. **전부 이 가이드대로 하나씩 따라 하면 이제는 안 겪어도 되는 문제들입니다.**

1. **db01 bond0에 web01의 IP가 잘못 들어감(IP 충돌)** — bond0 설정할 때 다른 서버 창의 명령어를 복사하다 IP를 안 바꾸는 실수가 was01에 이어 db01에서도 반복됐습니다. `ip a show bond0`에 10.10.10.13이 아니라 10.10.10.11(web01 것)이 떠 있었고, PostgreSQL 로그에 `could not bind IPv4 address "10.10.10.13": Cannot assign requested address`가 그대로 찍혀 있어 확인했습니다. §3-5에 재발 방지용 확인 절차를 추가했습니다.
2. **PostgreSQL `listen_addresses`가 설정 파일엔 맞는데도 반영 안 됨** — 위 IP 충돌 때문에 애초에 bond0에 10.10.10.13 자체가 없어서 벌어진 연쇄 문제였습니다. bond0 IP를 고치고 `systemctl restart postgresql` 하니 바로 해결됐습니다(§6-7).
3. **pom.xml이 XML로서 깨짐** — `<parent>` 조각을 붙여넣다가 감싸는 `<project>...</project>` 태그까지 같이 지워진 상태였습니다. §5-6에 전체 pom.xml을 완성본으로 넣었습니다.
4. **개발 PC(Windows)에 Maven이 아예 없음** — `mvn` 명령을 못 찾는 문제. 프로젝트에 이미 들어있는 Maven Wrapper(`mvnw.cmd`)로 해결했습니다(설치 불필요). §5-6에 확인 절차 추가.
5. **`mvn package`가 로컬에서 테스트 실패로 멈춤** — 자동 실행되는 컨텍스트 로드 테스트가 `10.10.10.13`(db01)에 접속을 시도하는데, 그 대역은 VirtualBox 내부 전용망이라 **호스트 PC에서는 원래 안 닿습니다.** `-DskipTests`로 해결. §5-6에 반영.
6. **컨트롤러/메인 클래스 실제 이름 확인** — 예시로 든 `Application.java`가 아니라 실제 프로젝트의 메인 클래스는 `AppApplication.java`(패키지 `com.example.app`)였습니다. §5-6 예시 코드를 실제 이름으로 통일했습니다.
7. **Rocky 최소 설치엔 `unzip`이 없음** — war 내용물 확인 시 `unzip: command not found`. `unzip` 대신 JDK에 포함된 `jar tf`로 대체하거나, §3-4에 `unzip`을 공통 설치 목록에 추가했습니다.
8. **`curl -o /var/lib/tomcat/webapps/app.war ...`에서 `sudo` 빠뜨림** — `/var/lib/tomcat/webapps/`는 `tomcat` 계정 소유라 일반 계정으로 쓰기가 막혀 `Permission denied`가 났고, 파일을 다 못 받고 강제 종료되면서 개발 PC의 `python -m http.server`가 `ConnectionResetError`를 내는 것처럼 보였습니다(파이썬 서버 자체는 문제 없었습니다). §5-6의 배포 명령에 `sudo`를 명시했습니다.
9. **Windows PowerShell에서 `curl`이 진짜 curl이 아님** — PowerShell의 `curl`은 `Invoke-WebRequest` 별칭이라 404 등 비-200 응답에서 빨간 예외를 던집니다(버그 아님). `curl.exe`를 쓰거나 브라우저로 확인하면 리눅스와 동일하게 동작합니다. §7에 반영.

## 이전 v3/v4 개정에서 고친 것 (참고용, 계속 유효)

지난 세션들에서 web01/was01/db01 실제 로그를 기준으로 문서 전체를 다시 맞춘 내용들입니다. 최신 상태는 위 v5 항목이고, 아래는 그 이전에 고쳐서 계속 유효한 것들입니다.

- **PostgreSQL 버전**: §4-6에서 `postgresql-server`를 버전 지정 없이 받아 Rocky 10 기본 저장소의 **PostgreSQL 16.14**가 설치됨. 원본 구성도의 15를 PGDG로 새로 깔면 인터넷 필요 + 기존 16과 파일 충돌 위험이 있어, **16을 그대로 채택**(Java 17→21과 같은 맥락의 버전 차이 인정).
- **db01 `lvm2` 누락**: `pvcreate: command not found` → `lvm2`가 §4-6 로컬 저장소 다운로드 목록에 없었음 → 추가.
- **was01 Tomcat 설치 방식**: tar 수동 설치가 아니라 실제로는 §4-6 로컬 저장소를 통한 **RPM 패키지(`tomcat9`) 설치**. 서비스명 `tomcat`, `CATALINA_BASE=/usr/share/tomcat`, 웹앱 경로 `/var/lib/tomcat/webapps/`.
- **AJP 커넥터 미반영**: `/opt/tomcat/conf/server.xml`(안 쓰이는 파일)을 고쳤던 문제 → 실제 `CATALINA_BASE`인 `/usr/share/tomcat/conf/server.xml`로 정정, `ss -tnlp`로 8009 확인 단계 추가.
- **Spring Boot ↔ Tomcat 버전 궁합**: 빌드된 앱이 Spring Boot 4.1.1(Jakarta EE, Tomcat10.1+ 필요)인데 설치된 건 Tomcat9(javax EE) → **Tomcat9 유지 + Spring Boot 2.7.18로 되돌리는 것으로 최종 확정**(§5-6). 이미 검증된 Tomcat9+AJP 인프라를 안 건드리는 방향이 실습에서 가장 안전했습니다.
- **DB 연동 확인용 컨트롤러 경로 버그**: `@GetMapping("/app/db-check")`로 예시를 드렸는데, WAR 파일명이 `app.war`라 Tomcat이 이미 컨텍스트 경로로 `/app`을 붙이는 상태라 중복돼 404. `@GetMapping("/db-check")`로 수정.
